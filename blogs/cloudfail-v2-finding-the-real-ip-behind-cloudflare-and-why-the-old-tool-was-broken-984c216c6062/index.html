CloudFail v2: Finding the Real IP Behind Cloudflare (And Why the Old Tool Was Broken)

Anmol K Sachan · February 25, 2026 · 3 min read
Share: Tweet Share View on Medium ↗

So I’ve been doing a lot of recon work lately and kept running into the same wall, Cloudflare. Great for the people running sites, genuinely annoying for those of us doing authorized pen tests. The classic move is to look for origin IP leaks, and for years, CloudFail was the go-to tool for that. The problem is, the original version by m0rtem basically stopped working. crt.sh timeouts, DNSDumpster throwing CSRF errors, BufferOver returning 403s. You’d run it and get a wall of red.

That’s what pushed me toward CloudFail v2.

So I picked up the project and did a proper rebuild, not a cosmetic update, an actual ground-up rewrite. I spent a weekend with it, and honestly, it’s a different tool.

What was actually broken in v1

The original used a brittle DNSDumpster scraper that relied on parsing CSRF tokens from HTML. The moment DNSDumpster changed its layout, which they did, the whole thing died. BufferOver went 403-only at some point. crt.sh queries had no retry logic, so a single 502 would kill the run. AlienVault OTX would 429 you, and that was that, scan over.

None of these failures was graceful. It just crashed.

What v2 actually fixes

The HTTP layer is completely different now. Everything goes through a central session with proper retry logic, five attempts, exponential backoff, covers 429s and 502s, and the full 5xx range. So when crt.sh hiccups, the tool waits, retries, and moves on instead of dying.

DNSDumpster scraping is just gone. Replaced with sources that actually work: AnubisDB, RapidDNS, ThreatMiner, URLScan, and the Wayback CDX API. crt.sh is still there, but now with dual query paths and proper backoff. CertSpotter is the primary CT source. Seven passive sources running concurrently, so even if two or three are having a bad day, you still get data.

The OTX fix is something I specifically appreciated. It detects the 429, backs off four seconds, then eight, then skips entirely and logs a warning. Scan keeps running. That’s how it should work.

Censys v2 was another broken one in a lot of tools. The old SDK-based approach had redirect issues. v2 talks to the REST API directly, handles 302s properly, and gives you meaningful error messages if your credentials are wrong or your plan doesn’t cover the query.

Running it

pip install -r requirements.txt
python -m cloudfail -t target.com --confirm-scope

With API keys:

python -m cloudfail -t target.com --censys-api-token YOUR_TOKEN --shodan-api YOUR_KEY --confirm-scope

Note: put it all on one line or be very careful with your shell’s line continuation. Trailing spaces after backslashes will silently break the command in zsh.

--passive-only skips the subdomain wordlist brute force if you just want the quick passive pass. --debug gives you full HTTP traces if something isn't working. --quiet plus --output json is what I use when piping results into something else.

Does it actually find origins?

On my authorized targets, yeah. The passive DNS aggregation across multiple sources catches historical IPs that predate Cloudflare being added. Subdomains that were never proxied — mail servers, staging environments, internal-facing stuff — show up through CT logs. The Wayback CDX source is underrated; it pulls historical URLs, and you’d be surprised what was resolving to a bare IP two years ago.

The ASN enrichment in phase four is a nice touch. Non-CF IPs get looked up, classified, and given a confidence score. Not perfect, but useful for triaging a large result set quickly.

Where to get it

v2 (the rewrite): https://github.com/anmolksachan/CloudFail/

Original v1 if you’re curious what it looked like before: https://github.com/m0rtem/CloudFail.git

Worth starring the v2 repo. It’s the only version of this tool I’d actually use for anything real right now.

Standard disclaimer applies; only run this against targets you have explicit written authorization to test. Cloudflare also has ToS around this kind of discovery, so be aware of the context you’re operating in.
