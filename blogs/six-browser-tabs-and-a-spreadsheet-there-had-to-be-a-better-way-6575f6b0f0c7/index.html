Six Browser Tabs and a Spreadsheet. There Had to Be a Better Way.

Anmol K Sachan · February 20, 2026 · 13 min read
Share: Tweet Share View on Medium ↗

ThreatTracer does in one command what used to take me 40 minutes of manual lookups.

Late into a pentest engagement last year, I found myself doing something embarrassing. I had discovered that the target was running an older version of Apache Struts, the kind of version that makes your eyes go wide because you know the history. So I opened NVD in one tab. Exploit-DB in another. GitHub in a third. Sploitus in a fourth. I had the CISA KEV catalog bookmarked because I’d started checking it manually after a client asked me if a vulnerability was “actively exploited” and I didn’t have a fast answer. Then I needed to check if there was a Nuclei template so I could actually confirm the finding before writing it up.

Six tabs. A bunch of copy-pasting CVE IDs back and forth. A running notes document where I was manually tracking which CVEs had working PoCs and which didn’t. And this was for one component on one host.

I’m not proud of how long that took. But I also suspect it’s exactly what most people doing this work are doing, because the data exists across a dozen different places and nobody had built a single tool that pulled it all together.

ThreatTracer is that tool. And this post is a proper walkthrough of how to actually use it, not just the happy path, but the filtering, the piping, the batch scanning, all of it.

Before We Get Into It

ThreatTracer was originally created by @FR13ND0x7F (Me), @0xCaretaker, and @meppohak5. The version we’re covering here, v4.1, is a major architectural rewrite of the old version, adding async scanning, CISA KEV integration, Nuclei template lookup, Metasploit module discovery, and the new asset scanning feature. The GitHub is at https://github.com/anmolksachan/ThreatTracer.

What It Actually Does (The Short Version)

You give ThreatTracer one of three things (PS it does a lot more):

  • A product name and version (apache, 2.4.51)
  • A live URL (https://target.com)
  • A CVE ID (CVE-2021-44228)

It returns everything relevant to exploitation: the CVEs, their CVSS scores, EPSS probability scores, whether CISA has confirmed active exploitation, Exploit-DB entries, GitHub PoC repositories sorted by star count (so you’re not digging through dead forks), whether a Nuclei template exists that you can fire immediately, and whether there’s a Metasploit module ready to go.

All of that, in parallel. One command.

Installation

git clone https://github.com/anmolksachan/ThreatTracer.git
cd ThreatTracer
pip install -e .

That gives you the threattracer command. If you're doing asset scanning (more on that shortly), also run:

pip install python-Wappalyzer

Wappalyzer adds fingerprinting for 1500+ technologies. The tool has its own header/body detection that works without it, but Wappalyzer catches a lot more edge cases, things like obscure CMSes, JavaScript frameworks, CDN signatures.

Tip: Use a virtual environment:

python -m venv venv && source venv/bin/activate
pip install -e .

API Keys

You don’t need them. But without an NVD API key, you’re limited to 5 requests per 30 seconds, which starts hurting the moment you’re scanning anything with a decent-sized CVE list. The free key takes about two minutes to get: https://nvd.nist.gov/developers/request-an-api-key

The GitHub token is more impactful than people expect. It unlocks the GitHub PoC search with star counts, Vulhub Docker environment discovery, and the Nuclei template index. Any token with public_repo scope works. https://github.com/settings/tokens

Store them once:

threattracer config --nvd-key YOUR_NVD_KEY
threattracer config --github-token ghp_yourtoken

After that, they load automatically. You never have to pass them again.

The scan Command

Three modes. All of them are useful in different situations.

Mode 1: Component name + version

The one I use most during pentests. You find something running on a host, you throw the name and version at ThreatTracer, and you get the full picture.

threattracer scan -c apache -v 2.4.51

The CPE matching is smarter than most people expect. It uses fuzzy similarity scoring, so typing apache correctly resolves to apache:http_server without needing the exact NVD vendor string. It queries the top matching CPEs in parallel rather than one at a time, deduplicates the results, and enriches everything simultaneously.

What comes back is a table with columns that are actually about exploitation, not just severity:

Sev   CVE ID             CVSS   EPSS%   AV     PR    EDB  PoC  Nuclei  MSF  KEV   Published
🔴    CVE-2021-41773     9.8    56.3%   NET    NONE   ✓    ✓     ✓      ✓   🔥   2021-10-05
🟠    CVE-2021-42013     9.8    43.1%   NET    NONE   ✓    ✓     ✓      ✓   🔥   2021-10-07
🟡    CVE-2022-31813     7.5     4.2%   NET    NONE   ✗    ✓     ✗      ✗        2022-06-08

That 🔥 Under KEV is the most important column on the table. It means CISA has confirmed this vulnerability is being actively exploited in real environments by ransomware groups, by nation-state actors, by whoever. You don't need to speculate about exploitability. Someone's already exploiting it.

Add --detail to get the full breakdown per CVE:

threattracer scan -c log4j -v 2.14.1 --detail

For Log4Shell, that panel shows CVSS 10.0, EPSS 97.5%, KEV entry with the date added and ransomware use confirmed, two Exploit-DB entries, five GitHub PoC repos sorted by stars (so the 2.4k-star one is at the top, not buried), a Vulhub Docker environment you can spin up to practice the exploit, a Nuclei template with the exact run command, and the Metasploit module path. And at the bottom, quick links to NVD, Sploitus, PacketStorm, and GitHub search, all clickable from the terminal if your terminal supports it.

Mode 2: CVE ID directly

When someone sends you a CVE in a message and asks if you’re affected:

threattracer scan --cve CVE-2021-44228 --detail

Or when you’re triaging a scanner output and want to check each finding:

threattracer scan --cve CVE-2023-44487 --detail

CVE-2023–44487 is the HTTP/2 Rapid Reset DDoS, an interesting case where CVSS 7.5 doesn’t fully capture the real-world impact, but the KEV entry and EPSS score tell a different story.

Mode 3: CPE string

For situations where you want surgical precision and you already have the exact CPE:

threattracer scan --cpe "cpe:2.3:a:apache:log4j:2.14.1:*:*:*:*:*:*:*"

Filtering: The Part That Actually Saves Your Sanity

Apache 2.4 has something like 80+ CVEs in NVD. You don’t need to read 80 CVEs during a pentest. You need the dangerous, exploitable ones that matter right now.

# Only confirmed actively-exploited CVEs, worst first
threattracer scan -c apache -v 2.4 --sort kev
# Sort by EPSS — which ones are statistically most likely to be exploited soon
threattracer scan -c openssl -v 3.0.7 --sort epss
# Just criticals from the last three years
threattracer scan -c struts -v 2.5 --severity critical --since 2021
# Top 10 only
threattracer scan -c wordpress -v 5.8 --sort kev --limit 10

The --sort kev flag is the one I reach for first. It puts CISA KEV entries at the top, then falls back to CVSS score. That ordering reflects reality better than pure CVSS — a CVSS 7.8 that's actively exploited in ransomware campaigns is more urgent than a CVSS 9.8 that nobody's ever actually weaponised.

For reporting and piping into other tools:

# JSON
threattracer scan -c nginx -v 1.18 -o json
threattracer scan -c nginx -v 1.18 -o json | jq '.cves[] | select(.in_kev == true)'
threattracer scan -c nginx -v 1.18 -o json | jq '.summary'
# CSV — for client reports or ticketing systems
threattracer scan -c apache -v 2.4.51 -o csv > findings.csv

The CSV output includes columns for Exploit-DB links, PoC links, Nuclei template links, and MSF module paths. Paste it into a client deliverable template, and you’re 80% done with the evidence section.

The Asset Scanner: The Feature That Changed My Workflow

Before v4.1, you had to know what was running on a target before you could use ThreatTracer. Which meant running WhatWeb first, or checking response headers manually, or some other step that added friction.

The asset command eliminates that step entirely.

threattracer asset https://target.com

It fetches the URL, follows redirects, reads all the HTTP response headers (Server, X-Powered-By, X-Generator, X-Drupal-Cache, all of it), fingerprints the HTML body for technology signatures, runs Wappalyzer if you have it installed, and for every technology it can identify a version for — it runs the full CVE + exploit scan automatically.

The output starts with what it found:

╭─ 🌐 Asset: https://target.com ─────────────────────────────────╮
│ Final URL:    https://www.target.com                             │
│ Status:       200                                                │
│ Server:       Apache/2.4.41 (Ubuntu)                            │
│ CVEs Found:   23    Critical: 4    Weaponised: 2                 │
╰──────────────────────────────────────────────────────────────────╯
Detected Technologies:
  Apache HTTP Server    2.4.41    95% confidence
  PHP                   7.4.3     90% confidence
  WordPress             5.7.1     85% confidence
  OpenSSL               1.1.1     75% confidence

Then below that: CVEs for each technology, same enrichment as always. One command, full picture.

A note on “Weaponised: 2” in that summary, that’s the count of CVEs where either a Metasploit module exists OR the CVE is in CISA KEV. The tool has a weaponised property specifically because there's a difference between "has a GitHub PoC" and "has an MSF module or is confirmed exploited in the wild." The latter is a stronger statement.

Batch Mode

This is where it gets genuinely useful for anything at scale.

Create a targets.txt:

# Scope for October engagement
# Lines starting with # are skipped
https://app.target.com
https://api.target.com
https://admin.target.com
https://staging.target.com
http://10.10.10.5:8080

Then:

threattracer asset --file targets.txt --concurrency 5

Five targets simultaneously. When it’s done, you get a summary table:

URL                         Status  Technologies                   CVEs  Crit  KEV  MSF
https://app.target.com        200   WordPress 6.1, PHP 8.0          12    2     1    0
https://api.target.com        200   Express, Node.js 16             4     0     0    0
https://admin.target.com      200   Apache 2.4.29, PHP 7.2          31    7     3    2
https://staging.target.com    200   nginx 1.14, PHP 8.1             8     1     0    1
http://10.10.10.5:8080        200   Jenkins 2.303                   17    4     2    3

That Jenkins host and the admin subdomain jump out immediately. 3 MSF modules on Jenkins. You know where you’re spending the next two hours.

The Part About EPSS That Most People Skip Over

CVSS scores are well understood. But EPSS is newer, and I think underused, so it’s worth a paragraph.

EPSS (Exploit Prediction Scoring System) is a probability score from FIRST.org. It runs from 0 to 1 and represents the likelihood that a given CVE will be exploited in the next 30 days, based on real threat intelligence data, what’s showing up in exploit kits, what’s being discussed in underground forums, and what’s being scanned for in the wild.

A CVE can be CVSS 9.8 and EPSS 0.003. That means it’s theoretically catastrophic, but practically nobody’s exploiting it — maybe because it requires specific configuration, or the affected software isn’t widely deployed, or there’s no reliable public exploit. Conversely, a CVE can be CVSS 5.4 and EPSS 0.88. That means real attackers are actively going after it despite the lower severity rating.

For pentesters, sorting by --sort epss on a list of CVEs gives you the ones most likely to have working, reliable exploits in the wild right now. It's a better signal than CVSS when you're deciding where to spend your time.

threattracer scan -c apache -v 2.4 --sort epss --limit 5 --detail

The Nuclei + MSF Integration, Concretely

When ThreatTracer finds a Nuclei template for a CVE, the detail panel includes:

Nuclei Templates (1):
  ▸ CVE-2021-44228  critical  https://github.com/projectdiscovery/nuclei-templates/...
  Run: nuclei -t cves/ -id cve-2021-44228

Copy that command, run it against your target, and you have a confirmed finding instead of a theoretical one. The difference matters when you’re writing a report.

When it finds a Metasploit module:

Metasploit Modules (1):
  ▸ [exploit] exploit/multi/misc/log4shell_header_injection
    Apache Log4j2 Remote Code Execution via JNDI injection in HTTP headers
  Run: msfconsole -q -x 'use exploit/multi/misc/log4shell_header_injection'

That’s not a description of what you could do. That’s the exact command.

Putting them together into a workflow:

# Find CVEs with Nuclei templates and fire them
threattracer scan -c nginx -v 1.14 -o json | \
  jq -r '.cves[] | select(.nuclei_templates | length > 0) | .cve_id' | \
  sort -u | \
  xargs -I{} nuclei -t cves/ -id {} -target https://target.com
# Find MSF module paths for everything exploitable
threattracer scan -c struts -v 2.3 -o json | \
  jq -r '.cves[] | select(.msf_modules | length > 0) | .msf_modules[0].fullname'

Bug Bounty Workflows

The EPSS + asset scanning combination is particularly useful for bug bounty triage, where you have a large scope and limited time. Higher EPSS correlates with CVEs that are actually exploitable (not just theoretical), which correlates with findings you can realistically demonstrate.

# Discovery pipeline
subfinder -d hackerone-target.com -silent | httpx -silent > live.txt
# Triage across all live subdomains
threattracer asset --file live.txt \
  --concurrency 10 \
  --severity critical,high \
  --sort epss \
  -o json > recon.json
# What has weaponised CVEs?
cat recon.json | jq '.[] | select(.weaponised_count > 0) | {url, weaponised_count}'
# Get Nuclei template IDs for everything testable
cat recon.json | \
  jq -r '.[].cve_results[].records[] | 
    select(.nuclei_templates | length > 0) | .cve_id' | \
  sort -u
# Fire Nuclei at a specific target
cat recon.json | \
  jq -r '.[].cve_results[].records[] |
    select(.nuclei_templates | length > 0) | .cve_id' | \
  sort -u | \
  xargs -I{} nuclei -t cves/ -id {} -target https://app.target.com

A Few Things That Aren’t Obvious

Version detection isn’t guaranteed. Some applications deliberately hide version information. When the asset scanner can’t determine a version for a technology, it shows the technology in the detected list but doesn’t run a CVE scan because querying NVD for “all WordPress CVEs ever” when you don’t know the version is noise, not signal. Take those unversioned detections as a prompt to go check manually.

GitHub PoC quality is variable. ThreatTracer sorts by stars and filters out forks, which cuts out most of the garbage, but a 50-star repo from two years ago might still be broken or incomplete. The source is shown alongside each PoC (trickest, github_api, vulhub) Vulhub entries are usually the most reliable for hands-on testing because they come with Docker environments that are actually maintained.

The cache is your friend on long engagements. Everything gets cached in ~/.threattracer/cache.db for 6 hours. Scanning the same target twice in a session is instant the second time. If you want to force fresh data:

threattracer cache-cmd --clear

The concurrency limit on batch scans is intentional. The default is 3 concurrent scans. You can push it higher (--concurrency 10) but keep in mind you're making actual HTTP requests to real targets. On a bug bounty program with rate limiting in scope, slamming 20 concurrent requests at all their subdomains simultaneously might get you banned before you've found anything useful.

The Practical Reality

Here’s what my workflow looks like on an engagement now (just an example), start to finish:

# 1. Find live targets
subfinder -d target.com -silent | httpx -silent > live.txt

# 2. Initial sweep - what's running, what's dangerous
threattracer asset --file live.txt --concurrency 5 --sort kev -o json > recon.json

# 3. Find the highest priority targets
cat recon.json | jq '.[] | select(.critical_count > 0) | 
  {url, critical_count, weaponised_count, 
   techs: [.technologies[] | {name, version}]}'

# 4. Deep dive on interesting targets
threattracer asset https://admin.target.com --detail --sort kev

# 5. Test confirmed findings
nuclei -t cves/ -id cve-2021-44228 -target https://admin.target.com

# 6. Export for the report
threattracer asset https://admin.target.com -o csv > admin-findings.csv

What used to take a morning of manual lookups is now a 20-minute automated sweep before I start actually testing anything. The manual work still happens, you still need to verify, to understand the context, to write the report intelligently. But you’re starting that manual work with a complete picture instead of building the picture piece by piece across six browser tabs.

Installing, in Full

# Clone
git clone https://github.com/anmolksachan/ThreatTracer.git
cd ThreatTracer
# Install
pip install -e .
# Optional: better asset fingerprinting
pip install python-Wappalyzer
# Set up keys (do this once)
threattracer config --nvd-key YOUR_NVD_KEY
threattracer config --github-token YOUR_GITHUB_TOKEN
# Test it
threattracer scan -c log4j -v 2.14.1 --detail

If you’re on a shared box or using a venv:

python -m venv venv && source venv/bin/activate
pip install -e .

That’s it. The ~/.threattracer/ directory is where it stores your keys, cache, and local Exploit-DB index. If anything goes sideways, rm -rf ~/.threattracer/ and start fresh.

threattracer asset --file targets.txt -o json > results.json
# Maintenance
threattracer sync                          # refresh exploit-db
threattracer cache-cmd --purge-expired    # clean stale cache
threattracer cache-cmd --clear            # wipe everything

Final Thought

None of the data that ThreatTracer surfaces is new or proprietary. NVD has been publicly accessible for decades. Exploit-DB has existed since 2006. CISA’s KEV catalog has been public since 2021. The Nuclei template repo is completely open. Metasploit modules are public. All of it is free.

The problem was never access to this information. It was the 40 minutes of switching tabs, copying CVE IDs, manually checking five separate systems, and trying to hold it all in your head simultaneously. That friction adds up. It’s the difference between doing thorough triage on every finding and doing thorough triage on the ones you have time for.

ThreatTracer is just friction removal. One command instead of six tabs.
